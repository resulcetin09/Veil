# Veil

**Access, without exposure.** Private invitation access built on Midnight for the Rise In Level 3 programme.

[![Compile, test & build](https://github.com/resulcetin09/Veil/actions/workflows/ci.yml/badge.svg)](https://github.com/resulcetin09/Veil/actions/workflows/ci.yml)

Veil lets a guest prove possession of an authorized invitation without publishing the invitation secret or identifying its allowlist entry. Every invitation can be redeemed once. An organizer can create an event, register invitations and seal the guest list from the app.

**Selected idea:** Private Allowlist Access. See the [product proposal](docs/product-proposal.md), [submission checklist](docs/submission.md), and [Turkish setup guide](docs/SETUP-TR.md).

## Status — read this first

The Compact contract, proof keys, application and local test suite are implemented. The wallet integration uses the real Midnight connector and providers. The local demo executes the generated contract in your browser, **without generating a zero-knowledge proof or sending a transaction**.

Public-network deployment and a real wallet-signed end-to-end transaction are separate acceptance checks. Until evidence is recorded in [submission.md](docs/submission.md), do not treat this project as a completed network deployment or an audited production service. Event proposal approval must come from the programme organizer.

The GitHub Pages workflow targets `https://resulcetin09.github.io/Veil/`; the link is usable after Pages is enabled and the deployment succeeds. The badge above reflects GitHub’s actual workflow status.

## Run locally

Use Node.js 24 and npm on macOS or Linux. Windows developers can use WSL.

```sh
npm ci
npm run setup:compact
npm run compile
npm run dev
```

Open `http://127.0.0.1:5173`. Select **Try the local demo** to explore without a wallet. The demo registers four random sample commitments, seals the allowlist, executes a real compiled `redeem` circuit and rejects a second redemption. Its receipts explicitly say `mode: demo` and are not network evidence.

The compiler installer downloads **Compact 0.31.1** from the official Midnight release and checks its SHA-256 digest. Compiler binaries, generated code and proving keys are regenerated rather than checked into Git.

## Use Midnight Preview

1. Install [Lace with Midnight support](https://www.lace.io/) and select **Preview**. Veil supports connector API **4.x**.
2. Fund the test wallet and ensure it has usable DUST for fees, following the [official Midnight setup](https://docs.midnight.network/getting-started/installation).
3. Install and start Docker, then run `docker compose up -d` in this project. This starts **proof-server 8.1.0**, bound only to `127.0.0.1:6300`.
4. In Lace, choose the local proof server at `http://localhost:6300`. Veil refuses a remote proof endpoint to avoid sending invitation witnesses to a third party.
5. Connect the wallet. Under **For organizers**, enter an event name and create the event. Approve the wallet transaction and wait for actual ledger confirmation.
6. Download the organizer recovery file. Keep it private; it authorizes invitation registration and sealing. It is not a wallet seed phrase.
7. Create each invitation and wait for confirmation before distributing its downloaded file. The contract supports up to **1,024** invitations.
8. Select **Seal allowlist** once every guest has an invitation. This is irreversible. Guests cannot redeem before sealing; new invitations cannot be added afterward.
9. A guest connects a Preview wallet, imports the invitation, reviews the disclosure and requests access. Veil generates a proof locally, asks the wallet to balance/sign, submits and waits for finalization.
10. Download the confirmed receipt. A second redemption must fail, even through a modified client.

Hosted HTTPS pages talking to a local proof server may require browser local-network permission and compatible proof-server CORS settings. If the browser blocks the request, run the application locally; do not bypass certificate warnings or disable browser protections.

### Recovery and limits

- Keep downloads before reloading or disconnecting. Private invitation and organizer material is intentionally held in memory, not localStorage, IndexedDB, URLs or analytics.
- The recovery file restores event operations through **Import recovery file**. A contract maintenance signing key generated by Midnight.js is session-only and is not exported by this app; contract upgrades are not a supported product feature. While that original session exists, the maintenance authority is an additional trust boundary.
- An uncertain network result is not failure evidence. Check the wallet/indexer before retrying an approved transaction. Keep a pending invitation file; never issue a replacement just because the browser timed out.
- A deployment whose confirmation is lost before its address is recovered needs manual wallet/indexer recovery. The current UI does not persist a pending deployment across reloads. Keep the tab open through confirmation.
- Only Preview is supported. No payments, token transfers, admission to a real venue, identity verification or mainnet use are included.

## Privacy model

### What a public observer can learn

- The event ID, organizer authorization commitment, registration status and public contract code.
- Allowlist commitments, the final Merkle root, list size and successful admission count.
- A domain-separated, event-scoped nullifier for each redeemed invitation.
- Transaction timing and public ledger metadata. This application makes no blanket promise to hide every wallet/network-level signal.

### What the membership proof does not disclose

- The random 256-bit invitation secret.
- Which specific allowlist commitment the guest used.
- The private Merkle path proving that commitment’s membership.
- Names, emails or identity documents; the application does not request them.

### How the contract enforces it

`invitationCommitment = persistentHash(["veil:invitation:v1", eventId, secret])`

`nullifier = persistentHash(["veil:nullifier:v1", eventId, secret])`

`register` verifies knowledge of the private organizer secret and inserts a commitment. `closeRegistration` permanently freezes the list. `redeem` checks that the privately supplied path’s leaf equals the commitment derived from the guest’s secret, checks the resulting public root, and rejects a previously spent nullifier. Only the root, nullifier and successful state transition are disclosed during redemption. It does **not** perform a public `registered.member(leaf)` check in the redemption circuit.

Freezing the tree prevents different guests from selecting historical roots with different anonymity sets. Tests include a malicious witness returning a different guest’s valid path, not only well-behaved witness implementations.

### Explicit trust boundaries

- **Organizer:** the organizer generates bearer secrets and may know whom they were sent to. An organizer who retains those secrets can compute nullifiers and correlate admissions. Veil does not claim anonymity from that organizer.
- **Device and proof service:** the local proof server processes private witness material. A compromised device, extension or modified application can leak it. In-memory storage is not a guarantee of secure memory erasure.
- **Delivery:** anyone who receives an invitation file can redeem it first. Do not attach real invitations or organizer files to public issues or this repository.
- **Anonymity set:** one guest provides no meaningful ambiguity. Timing, small groups and external knowledge can create correlations despite a valid zero-knowledge proof.
- **Maintenance authority:** the SDK deployment creates a maintenance authority. This app verifies deployed circuit keys before using a contract, but does not provide upgrade governance or a formal immutability guarantee.

Read the app’s **Privacy** view and [Midnight’s official private-data guidance](https://docs.midnight.network/concepts/how-midnight-works/keeping-data-private).

## Tests

```sh
npm run compile:check   # compile circuit code; skip expensive key generation
npm run typecheck
npm test               # generated-contract, invitation and wallet tests
npm run build
npm run test:e2e        # desktop + mobile, including axe WCAG AA checks
npm run test:e2e:dev    # demo + lazy SDK imports against the development server
```

The development checks cover successful demo admission, replay protection, a failed demo module download, and real SDK loading with a mocked wallet. The on-chain runtime is a direct pinned dependency so Vite can resolve it after dependency optimization; browser globals load before the application.

Local browser tests use installed Google Chrome. CI installs Chromium. To use downloaded Chromium locally, set `PLAYWRIGHT_CHANNEL=chromium` as documented in the configuration. Browser wallet mocks test UI behavior; they do not prove live wallet or network integration.

`npm run check` runs compilation, type checking, unit tests and build. `npm run compile` is required before a real deployment or release build because it generates the proving assets.

Test coverage includes valid admission, replay rejection, unregistered secrets, forged paths, malicious witness substitution, unauthorized organizer actions, duplicate registration, sealed-list enforcement, event/domain separation, public transcript disclosure, strict input parsing, wallet rejection, wrong networks and isolated private session state.

## CI/CD

[`.github/workflows/ci.yml`](.github/workflows/ci.yml) runs on every push and pull request:

1. Install locked dependencies and checksum-verified Compact.
2. Compile all three circuits and generate real proving/verifier keys.
3. Type-check, run contract/application tests, and build.
4. Run desktop/mobile browser and accessibility tests against the production build, plus demo and SDK regression checks against the development server.
5. Upload test reports and failure traces.
6. On `main`, build with `/Veil/` as the base path and deploy to GitHub Pages only after successful verification.

In GitHub, set **Settings → Pages → Source → GitHub Actions** before the deploy job runs. No wallet secrets belong in GitHub Actions. Contract deployment is wallet-driven from the application and is not automated by this pipeline.

## Architecture

```text
contracts/veil.compact       Public ledger and private membership circuits
contracts/managed/          Generated Compact output (ignored)
src/contract/witnesses.ts   Memory-only organizer and guest witnesses
src/lib/midnight.ts         Real providers, deployment, calls and confirmation
src/lib/wallet.ts           Connector discovery and network/session checks
src/lib/invitation.ts       Strict, bounded import/export format
src/lib/demo.ts             Explicit local circuit demonstration
src/components/             Guest, organizer, wallet and privacy experiences
tests/                     Contract and application unit tests
e2e/                       Browser and accessibility checks
docs/                      Proposal, setup, evidence and submission status
```

Pinned compatibility: Compact 0.31.1, Compact runtime 0.16.0, Compact.js 2.5.1, on-chain runtime 3.0.0, ledger 8.1.0, Midnight.js 4.1.1, connector 4.0.1, proof server 8.1.0. Based on the [official compatibility matrix](https://docs.midnight.network/relnotes/support-matrix).
